# Requirements traceability

Every requirement in the use case, mapped to how it is designed, where it is implemented, and which tests prove it. "Production" rows are additions a real payment platform needs that the use case does not spell out.

| # | Requirement (from the use case) | Design | Code | Proven by |
|---|---|---|---|---|
| R1 | Submit an ACH payment with customer id, source account, destination account, amount, reference | `POST /v1/payments`; strict schema (unknown fields rejected); amounts converted to integer cents | `api.py` `CreatePaymentRequest`, `payments.py` `create()`, `domain.py` `to_cents()` | `test_01`: PDF example accepted; exact cents; 11 invalid-input cases rejected with nothing stored |
| R2 | Lifecycle: PENDING, PROCESSING, COMPLETED, FAILED, RETRYING | State machine with 5 legal transitions; the **only** status-change function is `transition()`; also enforced by a database trigger | `domain.py` `TRANSITIONS`, `payments.py` `transition()`, `migrations/001_init.sql` `payments_guard` | `test_03`: all 25 status pairs checked; raw SQL illegal change refused; happy path chain |
| R3 | Not processed synchronously | API saves payment + job in one transaction and returns `202`; workers process later | `payments.py` `_create_in_tx()`, `worker.py` | `test_02`: bank not called during the request; job queued |
| R4 | Queue-based processing | PostgreSQL job table claimed with `FOR UPDATE SKIP LOCKED`; leases for crash recovery | `job_queue.py` | `test_02`: survives restart; 4 competing workers, 60 payments, each processed once |
| R5 | External bank API integrations | HTTP bank client classifies outcomes (accepted / rejected / retryable); payment id sent as the bank's idempotency key | `bank.py` `HttpBankGateway` | `test_03`: closed/invalid accounts fail without retry; bank timeout never pays twice |
| R6 | Retry handling | Exponential backoff with jitter, attempt cap, permanent vs. temporary errors, circuit breaker | `worker.py` `_record_outcome()`, `domain.py` `backoff_ms()`, `bank.py` `CircuitBreaker` | `test_03`: flaky bank retried to success; gives up at the cap; breaker opens and protects retry budgets |
| R7 | Prevent duplicate payment execution | `Idempotency-Key` (replay returns the original) + unique `(customer, reference)`, both enforced by database constraints; single-snapshot lookup | `payments.py` `_create_in_tx()`, `migrations/001_init.sql` unique constraints | `test_02`: replay, 422 key reuse, 409 reference reuse, 30 simultaneous identical requests → 1 payment, deterministic race regression test, raw SQL duplicate refused |
| R8 | Retrieve payment status | `GET /v1/payments/{id}`, plus list/filter with cursor pagination | `api.py`, `payments.py` `get()`, `list()` | `test_04`: status before/after processing; 404; pagination with nothing missed or repeated |
| R9 | Webhook status updates | Transactional outbox; signed (HMAC-SHA256, Stripe-style); retried with backoff; ordered per payment; manual retry; disable endpoint | `webhooks.py` | `test_04`: one signed webhook per change, in order; tamper/replay rejected; failing receiver retried; dead receiver doesn't block payments |
| R10 | All state changes traceable | Append-only `payment_events` written in the same transaction as each change: from, to, reason, actor, request id, metadata, time; database triggers block UPDATE/DELETE | `payments.py` `_record_event()`, `migrations/001_init.sql` | `test_04`: unbroken chain with reasons, actors, correlated request id; edits/deletes refused |
| R11 | Banks unavailable / network failures occur regularly; recover safely | Leases + fencing tokens, idempotent bank calls, circuit breaker, outbox | `job_queue.py`, `worker.py`, `bank.py` | `test_03`: worker crash after money moved → recovered without paying twice; zombie worker can't overwrite; `test_05` chaos |
| R12 | Observable | JSON logs with redaction, request ids end to end, Prometheus metrics, liveness/readiness | `logs.py`, `metrics.py`, `api.py` | `test_04` operations test |
| P1 | *Production:* authentication & tenant isolation | API keys stored as SHA-256 hashes; each request scoped to its customer; other customers' payments return 404 | `auth.py`, `api.py` `current_customer` | `test_01` authentication class |
| P2 | *Production:* abuse protection | Rate limiting per API key; request size limits; SSRF protection for webhook URLs (including DNS-rebinding defense) | `api.py` `RateLimiter`, `webhooks.py` `check_webhook_url()` | `test_01` rate limit; `test_04` SSRF |
| P3 | *Production:* data protection | Account numbers masked in responses, webhooks, and logs; payment terms immutable after submission | `mappers.py`, `logs.py`, `payments_guard` trigger | `test_01` masking; `test_03` immutable terms |
| P4 | *Production:* are the tests themselves trustworthy? | Mutation testing: 10 realistic bugs injected one at a time; each must make the evals fail | `scripts/mutation_check.py` | 10/10 caught |
